# 智能挖机真机录制规则与开发需求

## 1. 背景

我们现在准备在真机上正式录制智能挖机数据。在开始大规模录制之前，需要先确定 episode 的任务逻辑、录制规则，以及需要开发的辅助脚本。

当前录制目标不是让挖机连续自主作业，而是先采集高质量、可训练、可检查的人工操作数据，用于后续 ACT 等模仿学习模型训练。

为了降低学习难度，我们希望每条 episode 的初始条件尽量一致，包括：

- 挖机 4 个主要关节的初始位置尽量一致。
- 作业区土体状态尽量一致。
- 每条 episode 都从固定初始姿态开始，并最终回到固定初始姿态附近。

土体 reset 暂时不做自动化，由人工用铲子恢复。

## 2. 当前任务场景

当前真机录制的任务是一个完整的挖掘作业闭环：

```text
固定初始姿态
→ 在作业区挖一铲土
→ swing 旋转到倾倒区
→ 将土倾倒到倾倒区
→ 挖机返回初始姿态附近
→ go-home 脚本精确微调回固定初始姿态
→ episode 结束
```

也就是说，一条 episode 应该覆盖从固定初始姿态开始，到完成挖掘、旋转、倾倒，再回到固定初始姿态的完整闭环。

## 3. Episode 生命周期

每条 episode 的完整流程如下：

```text
1. 人工确认土体已经 reset 完成
2. 按 2 号按键，启动 recorder，开始新一轮 episode 录制
3. 挖机师傅从固定初始姿态开始操作
4. 完成一次挖土、旋转、倾倒
5. 挖机师傅把 4 个关节操作回 home pose 附近
6. 启动 go-home 脚本
7. go-home 脚本把 4 个关节精确拉回固定 home pose
8. go-home 返回 succeed / OK
9. recorder 自动停止，当前 episode 完成并落盘
10. 人工恢复土体
11. 再次按 2 号按键，开始下一条 episode
```

关键点：

- 录制开始由人工触发。
- 录制结束由 go-home 脚本成功事件触发。
- episode 结束后，receiver 不退出，recorder 停止。
- 人工恢复土体期间不录制。
- 土体恢复完成后，再由人工按 2 号键开始下一轮录制。

## 4. Episode 阶段标记逻辑

当前真机侧可用信息有限，阶段标记第一版只依赖以下信号：

- recorder / go-home 的状态事件。
- 4 个关节的位置和速度。
- 一路相机视频。

其中，一路相机第一版不用于自动判断阶段，只用于人工复核和后续视觉质量检查。阶段自动标记主要依赖 4 个关节的位置和速度，以及 go-home 脚本事件。

这里的“作业区”和“倾倒区”不要理解成通过传感器直接识别出来的土体区域，而是根据固定作业流程标定出来的关节空间范围，尤其是 swing 角度范围：

```text
dig_swing_range
  作业区对应的 swing 角度范围。

dump_swing_range
  倾倒区对应的 swing 角度范围。

home_joint_pose
  固定初始关节位置。

near_home_tolerance
  人工返回 home pose 附近时允许的粗容差。
```

第一版使用粗粒度阶段即可：

```text
DIG
  从 episode 开始，到 swing 角度明显离开作业区范围并持续朝倾倒区运动。

SWING_TO_DUMP
  从离开作业区 swing 范围，到进入倾倒区 swing 范围并开始 dump。

DUMP
  从 bucket 在倾倒区开始打开/卸料，到卸料动作结束并开始返回。

RETURN_NEAR_HOME
  从卸料结束后返回，到挖机 4 个关节回到 home pose 附近。

GO_HOME
  go-home 脚本接管并精确微调到固定 home pose。
```

推荐实现为单向状态机：

```text
DIG
→ SWING_TO_DUMP
→ DUMP
→ RETURN_NEAR_HOME
→ GO_HOME
→ END
```

阶段只允许按这个顺序向前切换，不允许因为瞬时抖动跳回前一个阶段。每个切换条件都应该增加 hysteresis / dwell time，例如条件连续满足 0.2 到 0.5 秒才切换，避免因为单帧噪声导致阶段反复变化。

阶段切换可以按以下逻辑判断：

```text
DIG → SWING_TO_DUMP
  swing_angle 离开 dig_swing_range；
  并且 swing_velocity 连续一段时间指向 dump_swing_range；
  可选：boom / arm / bucket 的姿态已经进入“抬斗/离土”区间。

SWING_TO_DUMP → DUMP
  swing_angle 进入 dump_swing_range；
  并且 swing_velocity 下降到接近停止；
  并且 bucket 角度或 bucket 角速度出现卸料动作。

DUMP → RETURN_NEAR_HOME
  bucket 卸料动作结束；
  并且 swing_velocity 开始持续指向 home / dig_swing_range；
  或者 distance_to_home_pose 开始持续减小。

RETURN_NEAR_HOME → GO_HOME
  4 个关节已经进入 home pose 附近的粗容差范围；
  并且 go-home 脚本被启动。

GO_HOME → END
  go-home 返回 succeed / OK；
  recorder 停止，episode 完成。
```

判断阶段时不要只看单一变量。推荐组合以下派生量：

```text
joint_position
joint_velocity
swing_angle
swing_velocity
bucket_angle
bucket_angular_velocity
in_dig_swing_range
in_dump_swing_range
distance_to_home_pose
go_home_running
go_home_result
```

其中最关键的是：

- `go_home_running` 和 `go_home_result`：用于确定 GO_HOME 和 END，优先级最高。
- `swing_angle` / `swing_velocity`：用于判断 swing_to_dump 和 return_near_home。
- `bucket_angle` / `bucket_angular_velocity`：用于判断 dump 开始和结束。
- `in_dig_swing_range` / `in_dump_swing_range`：用于判断挖机上车是否处于作业区方向或倾倒区方向。
- `distance_to_home_pose`：用于判断是否已经回到 home pose 附近。

如果第一版不想增加挖机师傅操作负担，阶段可以先通过离线 labeler 根据上述规则自动生成；如果后续发现边界不够稳定，再增加少量人工事件标记，例如 dump 开始、go-home 开始。

注意：在当前传感器配置下，系统无法直接知道“铲斗里是否真的有土”或“斗尖是否在真实土体边界内”。这些只能通过关节状态和固定作业区标定做近似判断。第一版 phase label 的目标不是精确理解土体交互，而是把 episode 稳定切成可训练、可筛选的粗阶段。

## 5. 需求一：go-home 控制脚本

需要开发一个 go-home 脚本，用于将挖机 4 个主要关节从“初始姿态附近的不确定位置”自动拉回“精确固定 home pose”。

### 5.1 使用边界

go-home 只负责 home pose 附近的微调，不负责从任意姿态大范围自主返回。

也就是说，挖机师傅需要先人工把挖机操作到 home pose 附近，然后再启动 go-home。

这样做的原因是：

- 降低自动控制风险。
- 避免脚本在远离 home pose 的状态下执行大幅动作。
- 保证每条 episode 的结束姿态足够一致。
- 保证下一条 episode 的初始关节状态足够一致。

### 5.2 输入

go-home 脚本需要至少支持以下输入：

- 当前 4 个关节的位置或角度。
- 目标 home pose。
- 每个关节允许误差 tolerance。
- 每个关节的安全速度限制。
- 每一步最大动作幅度限制。
- 超时时间。

### 5.3 输出

go-home 脚本需要返回明确结果：

```text
succeed / OK
failed
```

如果失败，需要给出失败原因，例如：

- 超时。
- 某个关节无法到位。
- 当前姿态距离 home pose 过远。
- 关节状态反馈异常。
- 控制指令发送失败。
- 通信异常。
- 急停或人工中断。

### 5.4 到位判定

go-home 的 succeed 必须基于真实关节反馈，而不是只看控制指令是否已经发出。

推荐判定逻辑：

```text
abs(current_joint[i] - target_home_joint[i]) < tolerance[i]
```

只有 4 个关节都进入 tolerance 范围，并且状态稳定一小段时间后，才返回 succeed。

### 5.5 安全要求

go-home 脚本必须有安全限制：

- 只能在 home pose 附近运行。
- 如果当前姿态距离 home pose 太远，应直接失败并提示人工先开回附近。
- 控制输出需要限幅。
- 控制速度需要限速。
- 需要支持超时退出。
- 需要支持人工中断或急停。
- 不允许突然大动作。

### 5.6 记录信息

建议记录 go-home 过程中的关键信息：

- go-home start timestamp。
- go-home end timestamp。
- target home pose。
- start joint state。
- final joint state。
- final joint error。
- go-home result。
- failed reason。
- go-home 期间的 joint state / action / timestamp。

## 6. 需求二：receiver 和 recorder 解耦

当前希望 Jetson 上的 receiver 和 recorder 分开。

### 6.1 receiver

receiver 是常驻进程，负责持续接收遥控器、手柄或上位机控制指令。

要求：

- receiver 一直运行。
- receiver 不应该因为某条 episode 录制结束而退出。
- receiver 不应该和 recorder 生命周期强绑定。
- recorder 停止后，receiver 仍然继续接收控制指令。

### 6.2 recorder

recorder 只负责当前 episode 的数据录制。

要求：

- 按 2 号按键开始新一条 episode。
- recorder 开始后记录 observation、joint state、timestamp、一路 camera 等数据；如果 receiver 侧已经有控制指令，也可以同步记录控制指令。
- go-home 返回 succeed 后，recorder 自动停止。
- recorder 停止后，episode 文件完整落盘。
- 人工恢复土体期间 recorder 不录制。
- 人工恢复完成后，再按 2 号按键开始下一条 episode。

### 6.3 录制开始与结束逻辑

录制开始：

```text
人工完成土体 reset
→ 按 2 号按键
→ recorder start
→ 新 episode 开始
```

录制结束：

```text
人工完成挖土、倾倒、返回 home pose 附近
→ 启动 go-home
→ go-home succeed
→ recorder stop
→ episode 文件落盘
```

注意：

- recorder 停止条件必须来自 go-home 的真实 succeed。
- 不应该在 go-home 刚启动时就停止 recorder。
- 如果 go-home failed，建议不要自动停止 recorder，或者至少把 episode 标记为 failed。

## 7. 需求三：主机实时 QC watcher

我们希望 Jetson 录制数据落盘之后，主机可以实时发现新 episode，并立即开始 QC。

目的不是立即训练，而是现场质量监控，及时发现物理链路或传感器问题。

### 7.1 背景

根据当前经验，真机物理链路和传感器连接不一定长期稳定。长时间录制时可能出现：

- 一路相机断流。
- 一路相机黑屏。
- 关节状态或速度信息缺失。
- timestamp 异常。
- 控制指令没有记录，前提是 receiver 侧本来计划同步保存控制指令。
- joint state 不更新。
- episode 文件损坏。
- 数据 shape 不符合预期。
- 图像重复帧过多。
- 图像空帧或坏帧。

如果等全部录完后再检查，可能会发现大量 episode 无效。因此需要边录边 QC。

### 7.2 QC watcher 逻辑

主机侧需要开发一个 watcher，持续监听数据目录：

```text
1. 主机持续 watch 数据目录
2. 发现新的 episode 文件完成落盘
3. 确认文件已经写完，不是正在写入状态
4. 自动运行 dataset QC / episode QC
5. 输出 QC 结果
6. 如果发现严重错误，及时提醒现场停止录制并排查
```

### 7.3 文件完成判定

需要避免 QC 读取一个仍在写入中的 episode 文件。

推荐做法：

```text
录制中使用临时文件名，例如 episode_000123.hdf5.tmp
写入完成并 close 文件后
rename 为正式文件名，例如 episode_000123.hdf5
watcher 只处理正式文件名
```

或者使用 done marker：

```text
episode_000123.hdf5
episode_000123.done
```

watcher 只有看到 `.done` 文件后才开始 QC。

## 8. 推荐状态机

建议把录制流程实现成一个明确状态机：

```text
IDLE
  等待人工按 2 号键开始录制

RECORDING
  正在录制人工操作 episode

WAIT_GO_HOME
  人工已经操作到 home pose 附近，等待或启动 go-home

GO_HOME_RUNNING
  go-home 脚本正在精调关节

GO_HOME_SUCCEEDED
  go-home 成功，准备停止 recorder

FINALIZING
  recorder 停止，episode 文件 close，写入 metadata，rename 为正式文件

DONE
  当前 episode 完成，等待人工 reset 土体

FAILED
  当前 episode 异常，需要人工处理
```

状态转换示例：

```text
IDLE --button_2_pressed--> RECORDING
RECORDING --operator_near_home--> WAIT_GO_HOME
WAIT_GO_HOME --start_go_home--> GO_HOME_RUNNING
GO_HOME_RUNNING --succeed--> GO_HOME_SUCCEEDED
GO_HOME_SUCCEEDED --stop_recorder--> FINALIZING
FINALIZING --file_committed--> DONE
DONE --button_2_pressed--> RECORDING
GO_HOME_RUNNING --failed--> FAILED
```

## 9. 整体验收标准

请实现或改造代码，使系统满足以下要求：

1. receiver 可以常驻运行，不受 recorder 启停影响。
2. 按 2 号键可以开始新的 episode 录制。
3. 每条 episode 从固定 home pose 开始。
4. 人工完成挖土、旋转、倾倒、返回 home pose 附近后，可以启动 go-home。
5. go-home 可以把 4 个关节稳定拉回固定 home pose。
6. go-home succeed 后，recorder 自动停止。
7. episode 文件完整落盘，并包含必要 metadata。
8. 如果 go-home failed，需要明确标记 episode 状态。
9. 主机可以实时 watch 新 episode，并自动运行 QC。
10. QC 能及时发现一路相机、关节状态、timestamp 等异常；如果录制控制指令，也需要检查控制指令异常。
11. QC 结果需要清晰输出，方便现场及时排查。
12. 不允许 QC 读取还在写入中的 episode 文件。

## 10. 特别注意事项

- go-home 只能作为精调脚本，不要假设它能从任意姿态安全返回。
- 挖机师傅需要先人工把挖机开到 home pose 附近，再启动 go-home。
- recorder 停止条件必须来自 go-home 的真实 succeed，而不是脚本启动。
- 如果 go-home failed，建议不要自动结束 recorder，或者至少将 episode 标记为 failed。
- episode 文件建议先写临时文件，写完后 rename 为正式文件，避免 QC 读取半成品。
- go-home 到位判定必须基于真实关节反馈。

## 11. 核心目标

这套录制规则和开发需求的核心目标是：

```text
让真机数据采集形成稳定闭环。
每条 episode 从固定初始姿态开始，
完成一次挖掘和倾倒任务，
再回到固定初始姿态结束。
同时通过实时 QC 保障录制质量，
及时发现传感器、链路和数据记录问题。
```
